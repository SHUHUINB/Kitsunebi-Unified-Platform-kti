源码与功能清单  +  前后端分离架构设计

目标栈：Charles 管理台 · CCProxy 适配层 · 一花卡密 · WPE 封包编辑器 · MCP  |  服务器 203.0.113.10  |  盘点日期 2026-09-26
盘点方式：源码静态读取 + 线上 md5 比对 未执行项已单独标注

结论摘要

  • 现状是「三个独立系统 + 一台反向代理」，不是一套平台。管理台（Python）把适配层（Python）和一花（PHP + MySQL）用 HTTP 反代硬缝在一起，前端是无框架的原生 JS。
  • 源码树分裂：管理台有两份副本，_net/charles_console/ 是 01:18 的过时版本，_deploy/ccpx/ 才是线上权威（md5 已比对）。重构前必须先收敛成单一事实源。
  • 鉴权规则有三套：/api/* 校验 token、/yh/** 必须绕过 CSRF、静态资源完全不校验。这是补丁堆出来的，不是设计出来的。
  • 重写范围：管理台后端 3359 行 + 前端 3564 行 + 一花 PHP 约 8042 行。适配层 4044 行不建议重写——它是真在跑的代理核心，风险远大于收益。
  • 目标形态：前端 SPA（Vue3+Vite）＋ 统一 API 后端（FastAPI）＋ 数据层收敛；一花先做适配器保留，再迁数据下线 PHP。

路由位置约束功能
/api/login /api/logout必须在鉴权之前登录 / 登出
/yh/*必须在 _csrf_ok() 之前一花表单 / ajax 提交（jQuery 不带 X-CC 头）

/api/ccpx/add /edit /delete过 CSRF账号增改删（转成 CCProxy 表单格式）

这四道「必须在谁之前」就是现状架构的病历。 一个 handler 里混着鉴权、CSRF、反代、静态资源四类关注点，顺序错一个就是 403 或白屏。重构的第一价值就是把这四条约束消掉。

4. 现状架构问题（带证据）

#问题证据后果
1源码树分裂_net/charles_console/server.py 与 _deploy/ccpx/_console_server.py 两份，md5 不同改错文件 = 白干。新人无法判断哪份有效
2前端无框架无构建app.js 1658 行 + wpe.js 1412 行，靠全局函数 apiUrl/esc/toast/show 互相依赖改一处崩一片；无法做类型检查与单元测试
3三套鉴权规则/api/* 校验 token；/yh/** 必须绕过 CSRF；静态资源完全不校验安全边界靠「顺序」维持，加一条路由就要重新推理一遍
4关注点全挤在一个 handlerdo_GET/do_POST 里同时有鉴权、CSRF、反代、静态资源、MCP路由顺序成为隐性契约（注释里写着「必须在 X 之前」×4）
5一花是异构系统PHP + 独立 MySQL，被反代塞进 /yh/；其 code 返回值不可信，必须直读数据库同一个「账号」在三处有不同表示，一致性靠人工
6MCP 是后加的挂在 HTTP handler 内，与 REST 路由混在同一个 do_POST协议演进会继续污染业务路由
7静态资源泄露配置路径/modules.js 无鉴权可读，暴露全部 107 个配置路径信息泄露；但直接加鉴权会导致页面白屏（<script src> 不带 token）

关键决策

层选型理由
前端Vue 3 + Vite + Pinia组件化拆掉 3564 行原生 JS；构建产物 hash 命名解决静态资源缓存与泄露；类型检查与单测成为可能
后端FastAPI依赖注入天然适合「鉴权一处」；自动 OpenAPI 直接成为前端契约；异步适配长轮询与 SSE
适配层原样保留（Python，:8888/:8889/:8893）真在承载流量，UDP 自愈/SOCKS5/CONNECT 都是踩坑产物，重写风险远大于收益
一花阶段一适配器保留 → 阶段二数据层收敛8042 行 PHP 一次性重写风险过高；先用适配器包成 REST，验证等价后再迁数据、下线 PHP
数据层SQLite → PostgreSQL先沿用 SQLite 降低迁移风险；三系统账号模型统一后视并发量再升
鉴权统一 JWT / HttpOnly Cookie消除「token 在 query 里传」「/yh/** 绕过 CSRF」这两类历史包袱

6. 迁移路线

阶段内容验收判据
P0
收敛		 删除/归档 _net/charles_console/ 过时副本；确立 _deploy/ccpx/ 为唯一事实源；把三系统源码集中到 _rewrite/ 下 全仓库只有一个 server.py；md5 与线上一致
P1
后端骨架		 FastAPI 起骨架；把现有 35 条路由按域拆成路由模块；鉴权收敛到一处；OpenAPI 自动生成 新后端能 1:1 覆盖旧路由；/api/v1/** 与旧 /api/* 可并行运行对比
P2
前端骨架		 Vue3+Vite 起项目；先迁移 WPE 封包编辑器（功能最独立、现有前端最规范）作为试点 WPE 页面在 SPA 中功能与旧版逐项对齐（13 项功能 + 全部元素 id）
P3
全量前端		 迁移 Charles 配置 / 概览 / 日志 / 备份 / 证书；一花后台用 Vue 重画，后端走适配器 旧 app.js/modules.js/wpe.js 可下线
P4
卡密收敛		 一花数据迁入统一数据层；PHP 下线；账号模型三处合一 卡密/账号/用户只存在一处数据源；一花 PHP 进程停止
P5
切换		 Nginx 前置；新旧并行 → 灰度 → 全量；旧栈归档 回归全绿；回滚路径可用
贯穿全程的硬约束（沿用现有纪律）： 先备份 → 上传后三方 md5 比对 → 远端语法检查 → 属主正确 → 回归必跑。 重构期间旧栈保持可运行，新栈并行验证，不做「一次性切换」。
