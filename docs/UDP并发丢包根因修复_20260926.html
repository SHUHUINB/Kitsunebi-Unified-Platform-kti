一、现象

用户要求「所有流量数据包一个都不能放过」。共享单端口 UDP 中继上线后，单连接 DNS 查询可正常往返，但并发场景下稳定丢包：

并发数成功耗时结论
33 / 30.2s看似正常
54 / 512.1s开始丢
107 / 1012.1s丢 30%
2015 / 2012.1s丢 25%

特征：零串包（回包 qname 全部对得上），全部走同一端口 8888（共享模式生效）。12.1s 是测试客户端的 UDP 接收超时，说明失败项是「一直没等到回包」。

三个失败关联在 05.896–05.915 就结束了，而它们的 DNS 回包在 05.877–05.940 才陆续到达。 关联提前结束 → 上游 socket 被关闭 → 在途 DNS 应答被内核丢弃（ICMP port unreachable）。
这就是「回包没进 usock」的完整解释。

三、根因

问题出在 _udp_associate_shared() 的 watch_control()：TCP 控制连接一断，立刻 stop.set()，紧接着 finally 里 usock.close()。

为什么这会造成丢包？因为共享模式下「哪条 TCP 配哪个 UDP 源」根本无法精确对应：

  • 所有关联共用同一个收包端口 8888，客户端源地址只能靠「首个数据包到达时认领」；
  • 认领策略只能按 IP + LIFO（同 IP 时优先认领最近建立的那条）；
  • 实测手机和电脑共用同一个 NAT 出口（都是 117.183.29.197），同 IP 下并发多条关联时，认领结果与「TCP 控制连接的归属」是错开的。

于是：某个客户端收到回包后关掉 TCP → 结束的是它自己那条关联，而那条关联的 usock 可能正在为另一条关联服务 → 一关就把对方还在路上的回包丢了。

这不是「共享模式设计错了」——回包路径本身是靠每条关联独立的上游 socket 区分的，天然不串包（实测 0 串包）。错的只是生命周期：控制连接断开时收摊太急。

四、修复

TCP 控制连接断开后，不立刻关闭上游 socket，给一个宽限期，让在途回包先发完：

# ccproxy_adapter.py · watch_control()
try:
    while True:
        if not await reader.read(4096):
            break
except Exception:
    pass

# 宽限期：TCP 断了不等于在途回包已经收完
grace = float(cfg.get("udp_control_grace", 3.0) or 0.0)
if grace > 0:
    log.info("UDP 关联控制连接断开 %s:%d，宽限 %.1fs 等在途回包",
             peer[0], peer[1], grace)
    await asyncio.sleep(grace)
assoc["stop"].set()

为什么是 3 秒：DNS 回包实测 50 ms 内到达，客户端 UDP 接收超时是 12 秒。3 秒足够覆盖任何在途回包，又不会让关联无谓地活着。

同时把收尾日志补上「数据源」字段，让 控制端口 → 数据源端口 的映射可见（以前只打控制端口，排查时看不出一对一关系）：

SOCKS5 UDP ASSOCIATE 中继结束（控制 117.183.29.197:1559 → 数据源 117.183.29.197:1069）
  上行 1 包/33 字节  下行 1 包/112 字节  裸包 0  早到 0  发失败 0

新增配置项 udp_control_grace（默认 3.0，设为 0 可退回旧行为）。

六、顺带收紧的运维项

核对抓包服务时发现磁盘风险：全量抓包峰值 27 GB/天（10 分钟写 188 MB），而清理原本每小时才跑一次。虽然「总量 ≤3 GB」的闸值能兜住，但清理一旦失败一天就会写满 23 GB 可用空间，服务全挂。

  • 清理 cron 由 17 * * * * 改为 */10 * * * *（每 10 分钟）；
  • 峰值占用从「3 GB + 1.1 GB」压到「3 GB + 0.2 GB」≈ 3.2 GB。
