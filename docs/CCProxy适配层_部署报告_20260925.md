日期：2026-09-25  
服务器：`203.0.113.10`（Ubuntu，Docker 部署一花卡密系统 `yihua-app` / `yihua-db`）  
目标：让一花卡密系统的**账号下发链路真正成立** —— 发卡 → 账号真实存在 → 到期真实断开 → 用户能用它当代理上网，且花瓶（Charles）继续干抓包/映射/验证页。

## 1. 一句话结论

一花说的是 **CCProxy 管理协议**，而花瓶不实现这套协议（配置里 `username`/`password` 零命中，客户端访问控制只有 IP 段白名单），所以原来的发卡链路是断的。本服务把这套协议实现出来，**卡密系统一行源码未改**：

```
一花卡密系统 ──CCProxy管理协议(GET/POST /account)──> ccpx 适配层 :8893
                                                       │
                                                       ├─ 账号库 SQLite（唯一真源 expire_at）
                                                       │
用户客户端 ──HTTP代理(账号密码) :8893 ──┐                │
用户客户端 ──SOCKS5(账号密码)   :8892 ──┴──> 适配层 ──> 花瓶 127.0.0.1:8888 ──> 外网
```

实测全链路通过：**5 层验证共 102 项，0 失败**。

## 3. 端口模型（复刻真 CCProxy）

真 CCProxy 的**管理页面和 HTTP 代理共用同一个端口**（默认 808）。一花的 `server_list.cport` 同时被当「通讯端口」（fsockopen 打 `/account`）和「代理端口」（用户侧连同一个口）用，所以这里也合流：

| 端口       | 作用                                                   | 鉴权                                 |
| -------- | ---------------------------------------------------- | ---------------------------------- |
| **8893** | 主端口：`/account`、`/status` 走管理面；其余走 HTTP 代理（含 CONNECT） | 管理面 `admin:<管理密码>`；代理面 `<账号>:<密码>` |
| **8892** | SOCKS5 代理                                            | `<账号>:<密码>`（RFC1929 用户名密码子协商）      |

两个面的凭据互不通用：管理密码不能当代理账号用（实测 407），用户账号也进不了管理面（实测 401）。

## 6. 协议三约束（改代码前必读）

一花用 9 条正则解析 `/account` 返回体，**没有 DOTALL**：

1. **每个 `<input>` 必须独占一行。** 正则 `/<input .* name="X" .* value="(.*?)"/ui` 里 `.` 不匹配换行。实测：两个 input 同行 → 只抓到 1 个；分两行 → 抓到 2 个。
2. **`name="X"` 与 `value=` 之间必须至少两个空格。** 实测：1 个空格 → **0 命中**；2/3 个空格 → 命中。（这条是自检第一次失败的真凶，靠二分定位到。）
3. **复选框 `checked` 的位置是硬编码字符下标。** 源码 `strripos(str_replace(['<','>','/'],'',$m),"checked") != "46"` —— 剥掉 `<>/` 后 `checked` 必须从下标 **46**（`enable`）/ **51**（`usepassword`、`autodisable`）开始，否则开关全反。

改动字面量后必须先跑 `--selftest`，它把这三点都锁住了（含「单空格必须 0 命中」的反向断言）。

## 7. 出口链语义（本次修掉的真 bug）

原来的实现在**所有**情况下都先让花瓶 `CONNECT host:80`，再把请求塞进这条裸隧道。结果普通 HTTP 一律 502。

排查过程中先把责任归错了地方 —— 一度以为是「Charles 不支持普通 HTTP 正向代理」。**实测推翻了它**：

```
direct   http://www.qq.com/      -> 302
charles  http://www.qq.com/      -> 302
charles  http://www.baidu.com/   -> 200
charles  http://example.com/     -> 200
charles  http://httpbin.org/ip   -> 200
```

花瓶对普通 HTTP 正向代理完全正常。错的是我们的走法：`CONNECT` 建的是「到目标 80 端口的裸隧道」，花瓶在隧道上不再解析 HTTP，抓包也就无从谈起；而且把绝对 URI 原样喂给隧道对面的源站，行为不可控。

**修正后的走法：**

| 客户端请求             | 走法                                     |
| ----------------- | -------------------------------------- |
| 普通 HTTP           | 直连花瓶 8888，把**绝对 URI 请求行**原样喂进去（正向代理语义） |
| CONNECT           | 让花瓶做 `CONNECT host:port`，隧道打通后双向透传     |
| CONNECT 但花瓶回非 200 | **回落直连目标**（`fallback_direct`）          |

新增两个开关：

```json
"fallback_direct": true,       // 花瓶拒收 CONNECT 时回落直连，而不是整条请求 502
"charles_bypass_ports": [],    // 这些目标端口不走花瓶，例如 [443] 避开证书固定的客户端
```

每条代理请求都会留痕 `-> charles` / `-> direct`，运维时一眼看出流量到底有没有过花瓶。

**顺带纠正一个误判**：`https://www.qq.com` 经花瓶回 501，一开始以为是花瓶的 SSL 代理白名单问题。看响应头才发现 `Server: stgw` + 跳 `waf.tencent.com/501page.html` —— **是腾讯侧 WAF 拦的**，不是花瓶。花瓶配置里 `sslLocations` 为空 = 对所有目标做 SSL 解密（`decryptSSL=true`），`https://www.baidu.com` / `taobao.com` / `github.com` 都是 200。

## 8. 到期语义

账号库只存事实，不存派生状态：**`expire_at` 是唯一真源**，`enabled` 只表示「手工禁用」。每次渲染时现算 `enabled AND now <= expire_at` 才勾选 `enable`。

所以「到期真实断开」**不需要任何定时任务**，也不会出现「改了 `disabledate` 但 `enabled` 字段忘了同步」的经典不一致。实测：改成昨天到期 → 下次 `GET /account` 立刻 `state=0` → 代理请求立刻 407。

## 9. 踩过的坑（都已定位并修掉）

| 现象                                                               | 根因                                                                                                                                | 处理                                                                                                     |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `POST /account` 的 body 永远读不到，add/edit/delete 全 0 账号              | `read_http_head` 把 `read(4096)` 多读到的字节丢了                                                                                          | 第三返回值改成「头之后多读到的字节」，POST/转发以它为初值续读                                                                      |
| `GET /account` 404                                               | 用 `request_line.partition(" ")` 把 `"/account HTTP/1.0"` 整段当 path                                                                  | 改 `request_line.split()` 取 `parts[1]`                                                                  |
| 自检报「username 0 个，enable 3 个」                                     | `CANON_TEXT` 字面量是 1 个空格                                                                                                           | 改 2 空格，并加 4b 组反向断言锁死                                                                                   |
| 容器访问 `203.0.113.10:8893` 超时                                    | **NAT 回环（hairpin）不被支持**，不是适配层问题                                                                                                   | `server_list.ip` 改 docker 网关 `172.20.0.1`（实测通）。终端用户不受影响：客户端是自己填服务器地址，`server_list.ip` 只用于后台的 fsockopen |
| 后台 API 一直跳 `login.php`                                           | 三重：① `cc_defender()` 拦截 → 带 `sec_defend` cookie；② **两个 `Cookie` 头**（PHP 只读第一个，`sub_admin_token` 丢了）→ 合并成一个头；③ token 生成脚本被 /tmp 清理 | 见下一条                                                                                                   |
| `cc_defender()` 为什么带任意 cookie 就过                                 | 源码判据 `!substr($_COOKIE['sec_defend'],0,32) === substr($iptoken,0,32)` —— PHP 运算符优先级导致**恒为 false**                                 | 带任意 `sec_defend` 即放行，不需要解那段 JS                                                                         |
| `sudo bash /tmp/x.sh` 两次 SIGTERM 空输出                             | 脚本经多层转义后为空                                                                                                                        | 改用 `bash -s` + stdin 传脚本                                                                               |
| `docker exec` 里 heredoc 被静默丢弃                                    | 少 `-i`，stdin 不转发                                                                                                                  | 统一加 `-i`                                                                                               |
| 公网 `8893` 返回 502 `upstream connect failed: connection timed out` | **腾讯云安全组未放行**                                                                                                                     | 见 §11                                                                                                  |

## 10. 安全整改（本次发现并已修复）

**问题**：两个诊断用 PHP 文件被留在了卡密系统的 webroot（`/opt/yihua/app/`，容器内 `/var/www/html`，对外入口是 `:8081`）：

- `_ccpx_mktoken.php` —— 用程序自己的 `authcode()` **吐后台管理会话 token**
- `_ccpx_probe.php` —— 能建/改/删 CCProxy 账号

**受控取证**（临时放回 → 请求 → 立即删除）：

```
http://127.0.0.1:8081/_ccpx_mktoken.php  ->  200，返回 83 字节 token
```

即**未鉴权就能执行**。GET 下 `$argv[1]/[2]` 取不到值，所以拿到的是空用户名/空密码的 token，**没有**直接泄漏 admin 会话；但「webroot 上有一个免鉴权就吐 token 的 PHP」本身不可接受 —— 一次改动、一处服务器配置差异，就会变成完整后台接管。

**处置**：

- 两个文件移到 `/opt/ccpx/tools/`（mode **0700 root**，不在 webroot）
- 新增 `/opt/ccpx/tools/mktoken.sh`：固定流程「拷进容器 → 跑 → 立刻删」，用 `trap` 保证异常也清理
- 复验：`http://127.0.0.1:8081/_ccpx_mktoken.php`、`_ccpx_probe.php` 均 **404**，容器内 webroot 无残留

**顺带纠正一个假信号**：`http://127.0.0.1:80/_xxx.php` 对任意不存在的 php 都返回 **200**（411 字节的 SPA 兜底页「SounBoot Cloud 控制台」）。`:80` 上的 nginx 服务的是另一个应用，不是卡密系统。判断卡密系统暴露面要看 **`:8081`**。

## 13. 诚实边界

- 全部结论来自本次在 `203.0.113.10` 上的**实际执行**，命令输出已逐条核对；无实机回读的项一律标注「未执行」，未做行为推断升级。
- 「102 项 0 失败」指的是上表五层的断言计数，不等于「生产环境零风险」：公网可达性（§11 第 1 项）尚未验证，因为安全组没放行 —— 这一项只有用户能在控制台完成。
- 花瓶链路的 SSL 解密行为对**证书固定的客户端**可能不兼容，需要按实际客户端在 `charles_bypass_ports` 里做排除，目前未做真实客户端实测。
